# Пользователи

При работе с Grav, с установленной админкой или без неё, есть несколько рекомендаций, которые стоит учитывать. Они касаются того, *кто* и к *чему* имеет доступ на вашем сайте, и потенциальных рисков, если не ограничивать эти факторы.

## Пользователи Grav и админка

При создании пользователей, которым будет доступна [админка](https://learn.getgrav.org/admin-panel), сначала подумайте, к чему они получат доступ. Плагин Admin предлагает надёжные [права доступа](https://learn.getgrav.org/admin-panel/dashboard/profile#access-levels), которые следует настроить так, чтобы ограничить возможности новых пользователей на сайте. Если пользователей много и некоторые из них будут только писать контент для сайта, им обычно нужно только разрешение `admin.pages` — а также обычные разрешения вроде `admin.login`.

Кроме того, всегда стоит следить за тем, чтобы у пользователей не было одного пароля на все случаи. Если кто-то украдёт их пароль, он сможет войти везде. Хороший пароль — это надёжный пароль, но даже длинная фраза из словарных слов подбирается легче, чем пароль из случайных символов, букв и цифр. Впрочем, человеку трудно запомнить длинный случайный пароль — [и тем более несколько](https://xkcd.com/936/), — поэтому [лучшая практика](https://support.google.com/accounts/answer/32040) — использовать [менеджер паролей](https://alternativeto.net/tag/encrypted-passwords/) и **никогда не повторять один и тот же пароль**. Многие также любят, чтобы браузер запоминал пароли для каждого сайта, а они помнили только один надёжный пароль для их разблокировки. Чтобы сгенерировать случайный пароль, достаточно открыть Блокнот и яростно нажимать случайные клавиши на клавиатуре.

Скажите пользователям использовать случайные пароли и придумать один надёжный длинный пароль, который они запомнят. Время от времени этот длинный пароль тоже нужно менять. А поскольку плагин Admin это поддерживает, им всегда следует использовать [двухфакторную аутентификацию](https://learn.getgrav.org/admin-panel/security/2fa). Чтобы предотвратить атаки перебором на админку, администратору также стоит включить [защиту от флуда](https://learn.getgrav.org/admin-panel/security/rate-limiting).

## Пользователи сервера и вебмастер

Вебмастер — это человек, отвечающий за поддержку сайта, и обычно у него есть доступ к серверу на уровне сервера. Ему, конечно, стоит [защитить сервер](https://learn.getgrav.org/security/server-side), но также убедиться, что он сам — и все остальные с доступом к серверу — подключаются к серверу только безопасным способом. Это значит, что **ни при каких обстоятельствах нельзя использовать протокол FTP**, только [SFTP](https://www.ssh.com/ssh/sftp/) с [парами ключей](https://www.ssh.com/ssh/public-key-authentication), защищёнными парольной фразой. Хостинг-провайдер обычно рассказывает, как отключить обычный FTP и подключаться к серверу по SFTP; создание пар ключей [хорошо описано](https://www.linode.com/docs/security/authentication/use-public-key-authentication-with-ssh/#generating-keys).

Шире говоря, подумайте, нужен ли доступ к серверу *кому-то ещё*. Каждый дополнительный пользователь с доступом — потенциальный риск, причём не только из-за своего поведения, но и из-за опасности, что при краже его ключей или паролей другие получат прямой доступ к серверу. В том же духе: **ни у одного пользователя не должно быть root-доступа** к серверу, а системный пользователь, под которым PHP работает для Grav, должен быть отдельным пользователем, доступным только системе.

Учитывая, насколько важен сервер для вашего сайта или сервиса, забота о его защите и содержимом должна быть первостепенной.
