# Раскрытие папки `user`

Панель администратора Grav может предупредить, если безобидный тестовый файл в приватном каталоге хранилища доступен напрямую через веб:

> Your web server is not applying Grav's access rules.

Относитесь к подтверждённому раскрытию данных серьёзно. В зависимости от каталогов и типов файлов, доступных с сервера, посетители могут скачать файлы учётных записей, конфигурацию, сохранённые отправленные формы или резервные копии всего сайта. Проверка использует безвредные файлы-маркеры; фактические приватные данные при этом не скачиваются.

В обновлённых версиях Admin2 и API проверяются файлы `.dat`, `.txt` и `.zip` в каталогах `user/data`, `backup` и `tmp`, а также выводятся найденные доступными комбинации каталогов и типов файлов. Старые версии проверяют только файл `.dat` в `user/data`; успешное прохождение этой проверки не означает, что другие типы файлов или каталоги защищены. Ошибки сети и неуспешные проверки не позволяют сделать однозначный вывод, а отсутствие предупреждения не является полноценным аудитом безопасности.

## Почему это происходит

Grav полагается на веб-сервер в вопросе запрета прямых запросов к своим приватным папкам. Блокировка перестаёт работать, когда:

- Вы используете **Apache**, но файлы `.htaccess` игнорируются, потому что `AllowOverride` установлен в `None` для корня вашего сайта. Это самая распространённая причина.
- Вы используете **Nginx**, **Caddy** или другой сервер, который вообще не читает `.htaccess`, а эквивалентные правила в конфигурацию сайта не добавлены.
- Прокси перед сервером самостоятельно отдаёт существующие статические файлы и перенаправляет только остальные запросы к PHP или Apache. В результате внешний сервер может предоставлять доступ к `.txt` и `.zip`, в то время как запросы к `.dat` доходят до Apache и получают ответ 403.
- Пользовательская или предоставленная хостингом конфигурация сервера заменила правила Grav без переноса этих блокировок.

## Как исправить

Цель на каждом сервере одна и та же: запретить прямой веб-доступ к `backup`, `tmp`, `logs`, `user/accounts`, `user/config`, `user/env` и `user/data`, при этом сохранив доступ к файлам, которые Grav предполагает сделать общедоступными, — изображениям аватаров в `user/accounts`, а также загруженным медиафайлам и ресурсам в `user/data`. Эти исключения должны располагаться перед соответствующим правилом запрета, иначе они никогда не сработают.

### Apache

Сначала убедитесь, что `.htaccess` учитывается. В вашем виртуальном хосте (или соответствующем блоке `<Directory>`) установите:

```apache
<Directory /var/www/grav>
    AllowOverride All
    Require all granted
</Directory>
```

Перезагрузите Apache (`sudo systemctl reload apache2` или `sudo apachectl graceful`). Сравните корневой `.htaccess` с текущей версией Grav и убедитесь, что он содержит эти правила; в старых версиях может отсутствовать `tmp`:

```apache
# Block private storage regardless of file extension
RewriteRule ^(backup|tmp|logs)/(.*) error [F,NC]
# Block all direct access to these sensitive user folders, whatever the file type
RewriteRule ^(user)/(config|env)/(.*) error [F,NC]
# Block user/accounts too, but allow avatar images to be served directly, whether
# stored at user/accounts/avatars/<file> or user/accounts/<username>/<file>
RewriteCond %{REQUEST_URI} !/user/accounts/[^/]+/[^/]+\.(jpe?g|png|gif|webp|avif|bmp|ico)$ [NC]
RewriteRule ^(user)/accounts/(.*) error [F,NC]
# Block user/data too, but allow public asset uploads (e.g. Flex Object images)
RewriteCond %{REQUEST_URI} !\.(jpe?g|png|gif|webp|avif|bmp|ico|mp4|webm|ogg|ogv|mov|mp3|wav|m4a|flac|pdf|woff2|woff|ttf|otf|eot|css|js)$ [NC]
RewriteRule ^(user)/data/(.*) error [F,NC]
```

Если вы не можете включить `AllowOverride`, скопируйте эти правила в конфигурацию вашего виртуального хоста вместо этого.

!!! note ""

    Если вы заменили или сильно отредактировали поставляемый `.htaccess`, сравните его с текущей версией в [репозитории Grav](https://github.com/getgrav/grav/blob/develop/.htaccess) и убедитесь, что блок Security присутствует.

### Nginx

Nginx не читает `.htaccess`. Сравните свою конфигурацию с поставляемым файлом `webserver-configs/nginx.conf` и добавьте эти блоки `location` перед универсальными обработчиками статических файлов. Скорректируйте пути, если Grav установлен в подкаталоге или использует пользовательские пути хранения:

```nginx
# deny private storage regardless of file extension
location ~* ^/(backup|tmp|logs)/ { return 403; }
# deny all direct access to these sensitive user folders, whatever the file type
location ~* ^/user/(config|env)/.*$ { return 403; }
# allow avatar images under user/accounts to be served directly, whether stored at
# user/accounts/avatars/<file> or user/accounts/<username>/<file>; this must come
# before the user/accounts deny so it wins the first-match
location ~* ^/user/accounts/[^/]+/[^/]+\.(jpe?g|png|gif|webp|avif|bmp|ico)$ { try_files $uri =404; }
# deny everything else under user/accounts
location ~* ^/user/accounts/.*$ { return 403; }
# allow public media uploads under user/data to be served directly;
# this must come before the user/data deny so it wins the match
location ~* ^/user/data/.*\.(jpe?g|png|gif|webp|avif|bmp|ico|mp4|webm|ogg|ogv|mov|mp3|wav|m4a|flac|pdf)$ { try_files $uri =404; }
# deny everything else under user/data
location ~* ^/user/data/.*$ { return 403; }
```

Затем перезагрузите Nginx (`sudo nginx -t && sudo systemctl reload nginx`). Полная рекомендуемая конфигурация описана в разделе [Nginx](/webservers-hosting/servers/nginx).

### Caddy

Caddy тоже игнорирует `.htaccess`. Сравните свою конфигурацию с поставляемым файлом `webserver-configs/Caddyfile`. Здесь важны два поведения Caddy, и при неправильной настройке оба проявляют себя без каких-либо ошибок:

- Сопоставитель `path` в Caddy использует буквальное сопоставление — он поддерживает подстановочные символы `*`, но **не является регулярным выражением**. Для всего, что требует альтернатив, классов символов или якорей, необходимо использовать `path_regexp`.
- За пределами блока `route` Caddy применяет собственный порядок директив, а глобальное перенаправление `try_files` выполняется до `respond`. Из-за этого все правила запрета перестают работать для любого пути, который Caddy не может сопоставить с файлом на диске. Поместите правила внутрь блока `route`, который выполняется сверху вниз в указанном порядке.

Сопоставители Caddy компилируются с помощью RE2 от Go, в котором нет поддержки lookbehind, поэтому для исключений медиафайлов используется отрицательный сопоставитель, а не встроенное в выражение условие:

```nginx
@denied_dirs path_regexp (?i)^/(\.git|cache|bin|logs|backups?|tmp|tests)/
@denied_user_config path_regexp (?i)^/user/(config|env)/
# block user/accounts, but allow avatar images to be served directly
@denied_user_accounts {
	path_regexp (?i)^/user/accounts/
	not path_regexp (?i)^/user/accounts/[^/]+/[^/]+\.(jpe?g|png|gif|webp|avif|bmp|ico)$
}
# block user/data, but allow public media uploads (e.g. Flex Object images)
@denied_user_data {
	path_regexp (?i)^/user/data/
	not path_regexp (?i)\.(jpe?g|png|gif|webp|avif|bmp|ico|mp4|webm|ogg|ogv|mov|mp3|wav|m4a|flac|pdf)$
}

route {
	respond @denied_dirs 403
	respond @denied_user_config 403
	respond @denied_user_accounts 403
	respond @denied_user_data 403

	# global rewrite should come last
	try_files {path} {path}/ /index.php?_url={uri}&{query}
	php_fastcgi 127.0.0.1:9000
	file_server
}
```

### LiteSpeed

LiteSpeed читает `.htaccess` и совместим с правилами Grav для Apache, поэтому достаточно включить поддержку `.htaccess` (аналог `AllowOverride All`). Убедитесь, что правила перезаписи включены для виртуального хоста.

### За обратным прокси, CDN или на управляемом хостинге

Если ваш сайт находится за обратным прокси или CDN, либо работает на управляемом/разделяемом хостинге, правила должны применяться на том слое, который реально отдаёт файлы. Если не уверены, какой сервер находится спереди — уточните у вашего хостера.

## Управляемые хостинги и хранилище за пределами корня веб-сервера

На хостингах вроде Cloudways выясните, какой стек обслуживает статические файлы. Правила Apache не могут защитить файл, который напрямую отдаётся nginx, даже если Apache работает за ним. Попросите хостинг применить правила запрета на внешнем сервере перед его универсальными обработчиками статических файлов. Блокировка доступа на уровне PHP не может перехватить такие запросы.

В версиях Grav с нативной поддержкой `.env` можно перенести резервные копии и временные загрузки, указав абсолютные пути в `.env` в корне Grav:

```dotenv
GRAV_BACKUP_PATH=/srv/private/grav-backups
GRAV_TMP_PATH=/srv/private/grav-tmp
```

Выбирайте каталоги за пределами корня веб-сервера и любых общедоступных алиасов сервера, доступные для записи процессу PHP. Эти настройки перенаправляют `backup://` и `tmp://`, но не перемещают и не удаляют старые файлы. Переместите существующие резервные копии из старого общедоступного каталога и удалите ненужные временные файлы, если установка или обновление не выполняется. Убедитесь, что прежние URL больше не возвращают содержимое файлов. Перенос этих каталогов не защищает `user/accounts`, `user/config` или сохранённые отправленные формы — для них по-прежнему нужны правила доступа.

Действие `save` плагина Form по умолчанию использует расширение `.txt`. На хостинге, который напрямую отдаёт `.txt`, но блокирует `.dat`, в качестве временной меры укажите `extension: dat` и убедитесь, что URL сохранённого файла недоступен. Само по себе расширение файла не является средством контроля доступа: стек только с nginx без правил запрета может отдавать оба типа файлов. Расширения `yaml`, `yml`, `json` и `md` могут блокироваться параметром `security.uploads_dangerous_extensions`; не отключайте эту защиту ради изменения формата сохранённых отправлений.

## Проверка исправления

После перезагрузки сервера вернитесь в панель управления. Предупреждение проверяется в реальном времени: Grav пытается скачать тестовый файл так же, как это сделал бы посетитель. Как только прямой доступ будет заблокирован, баннер исчезнет при следующей загрузке страницы.

Также можно вручную выполнить проверку, используя только безвредные файлы. Запишите короткий случайный маркер в новые файлы `.dat`, `.txt` и `.zip` в каждом проверяемом каталоге, запросите соответствующие URL без аутентификации и после этого удалите тестовые файлы. Ответ, содержащий маркер, подтверждает наличие доступа. Ответ 403 или 404 блокирует конкретно эту проверку; ошибка сервера, страница входа или неудачный запрос не подтверждают наличие защиты. Не используйте для проверки реальные резервные копии, файлы учётных записей или отправленные формы.

## Примечание о публичных медиафайлах в user/data

Grav намеренно разрешает прямую отдачу обычных изображений, аудио, видео и PDF-файлов из `user/data`, чтобы медиа, загруженные через Flex-объекты и подобные поля, продолжали работать. Это сделано по дизайну и не является причиной предупреждения. Предупреждение срабатывает только когда **не-медиа** файлы из ваших приватных папок становятся доступны. Для безопасной отдачи приватных или произвольных загруженных файлов лучше маршрутизировать их через прокси на уровне приложения, а не открывать папку напрямую.
