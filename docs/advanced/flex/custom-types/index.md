# Создание своего типа

Для многих сайтов главная причина взяться за Flex Objects — определить собственный тип данных: записи, которые слишком велики для конфигурации и недостаточно похожи на страницы, чтобы быть отдельными страницами. Справочник контактов, список событий, товары, отзывы и вакансии — всё это хорошие кандидаты.

Пользовательский тип определяется одним YAML-файлом **схемы**. Схема описывает форму редактирования, сообщает Grav, где хранятся данные, и управляет тем, как тип выглядит в Admin Next. Всё остальное (вид списка, REST API, шорткод фронтенда) предоставляется вам, как только схема существует.

Эта страница начинается с самой маленькой рабочей схемы, запускает её, а затем проходит через создание чуть более полного типа. Полный каталог всех параметров, которые принимает схема, см. в **[справочнике по схемам](blueprint-reference/index.md)**.

## Самая маленькая рабочая схема

Вот полный работающий справочник контактов. Сохраните его как `user/blueprints/flex-objects/contacts.yaml`. Имя файла (`contacts`) становится **именем типа**, которое вы будете использовать везде дальше.

```yaml
title: Contacts
description: A simple contact directory.
type: flex-objects   # не меняйте это значение

config:
  data:
    # Краткая форма хранения: один JSON-файл со всеми объектами
    storage: user-data://flex-objects/contacts.json
  admin:
    list:
      fields:
        name:
          link: edit
        email:

form:
  validation: loose
  fields:
    name:
      type: text
      label: Name
      validate:
        required: true
    email:
      type: email
      label: Email Address
```

Вот и всё. Два поля формы, одна строка хранилища и две колонки для списка в админке. Этого достаточно, чтобы Admin Next отрисовал рабочий интерфейс списка и редактирования, а REST API отдавал данные.

> [!IMPORTANT] Важно
> Строка `type: flex-objects` обязательна, и её нельзя менять. Именно она сообщает Grav, что этот YAML-файл — определение типа Flex, а не обычная форма или схема страницы.

### Активируйте его в Admin Next

Создать файл мало. Нужно включить схему, чтобы плагин узнал о ней. В Admin Next перейдите в **Plugins > Flex Objects** и добавьте путь к схеме в поле **directories**. Это дописывает путь в конфигурацию плагина, и именно это регистрирует тип. После сохранения очистите кэш, чтобы новый тип подхватился:

```bash
bin/grav clear
```

Перезагрузите Admin Next — и найдёте **Contacts** в области Flex Objects, готовый к добавлению и редактированию записей.

> [!TIP] Совет
> Если после сохранения тип не появился, почти всегда причина в том, что схема не включена в поле directories или кэш не очищен. Нужны оба шага.

### Что чему соответствует

Минимальная схема уже использует три самые важные части формата:

| Раздел | Назначение |
|---------|---------|
| `config.data.storage` | Где и как объекты хранятся на диске. |
| `config.admin.list.fields` | Какие колонки показывать в виде списка Admin Next. |
| `form.fields` | Форма редактирования (а значит, и поля, которые может содержать каждый объект). |

Это два обязательных ключа конфигурации (`config.data.storage` и `config.admin.list.fields`) плюс сама форма. Сделайте их правильно — и у вас рабочий тип.

## Создание небольшого настоящего типа

Давайте разовьём пример с контактами во что-то, что вы действительно могли бы выпустить: больше полей, разумный порядок по умолчанию и список с поиском. Это по-прежнему компактная схема, просто более полная.

```yaml
title: Contacts
description: Simple contact directory with tags.
type: flex-objects   # не меняйте это значение

config:
  data:
    storage: user-data://flex-objects/contacts.json
    ordering:
      last_name: ASC
    search:
      fields:
        - last_name
        - first_name
        - email
  admin:
    list:
      fields:
        last_name:
          link: edit
        first_name:
          link: edit
        email:
        website:
      options:
        per_page: 20
        order:
          by: last_name
          dir: asc
    menu:
      list:
        title: Contacts
        icon: address-card
        priority: 2

form:
  validation: loose
  fields:
    published:
      type: toggle
      label: Published
      highlight: 1
      default: 1
      options:
        1: PLUGIN_ADMIN.YES
        0: PLUGIN_ADMIN.NO
      validate:
        type: bool
        required: true
    last_name:
      type: text
      label: Last Name
      validate:
        required: true
    first_name:
      type: text
      label: First Name
      validate:
        required: true
    email:
      type: email
      label: Email Address
      validate:
        required: true
    website:
      type: url
      label: Website URL
    tags:
      type: selectize
      size: large
      label: Tags
      validate:
        type: commalist
```

Включите и очистите кэш точно так же, как раньше. Теперь у вас есть директория, которая сортирует записи по фамилии, позволяет администратору искать по трём полям и показывает аккуратный список из четырёх колонок. Блок `admin.menu.list` даёт ей отдельный пункт в боковой панели с иконкой и приоритетом.

Всё здесь — необязательное улучшение поверх минимальной версии. Добавляйте только то, что нужно, и когда нужно.

> [!NOTE] Примечание
> Форма выглядит одинаково независимо от того, пришла ли она со страницы, из файла конфигурации или из схемы плагина. Считайте `form.fields` формой, которую видит администратор, и следите, чтобы она содержала каждое поле, которое может хранить объект. Если вы уже умеете строить **[формы](../../../forms/index.md)**, вы уже умеете писать этот раздел.

## Устройство схемы

У каждой схемы Flex одинаковая структура верхнего уровня. Три ключа описывают тип, а три раздела — как он себя ведёт:

```yaml
title: Contacts               # понятное человеку название
description: A directory...    # краткое описание
type: flex-objects            # всегда flex-objects, не меняйте

config: {}       # хранилище, интерфейс админки, разрешения, шаблоны фронтенда
blueprints: {}   # форма настройки уровня директории (необязательно)
form: {}         # форма редактирования объекта и её поля
```

| Ключ | Что делает |
|-----|--------------|
| `title` | Название типа, как оно отображается в Admin Next. |
| `description` | Краткое описание директории. |
| `type` | Всегда `flex-objects`. Помечает файл как тип Flex. |
| `config` | Стратегия хранения, список, редактирование, меню и разрешения Admin Next, экспорт и поиск шаблонов фронтенда. |
| `blueprints` | Необязательная форма для конфигурации уровня директории (вид Configure). |
| `form` | Форма редактирования одного объекта, включая все его поля. |

Раздел `config` — самый большой и гибкий. Он охватывает стратегии хранения (SimpleStorage, FileStorage, FolderStorage), пользовательские классы объектов и коллекций, колонки списка, сортировку, поиск, меню боковой панели, разрешения и экспорт. Чтобы не повторять всё это здесь, исчерпывающий список параметров с примерами см. в **[справочнике по схемам](blueprint-reference/index.md)**.

> [!WARNING] Предупреждение
> Разрешения заслуживают особого внимания. Начиная с flex-objects 1.4.3 директория, схема которой не объявляет блок разрешений, закрыта для всех, кроме суперадминистраторов, по REST API. Если редакторам нужен доступ к вашему типу, нужно объявить блок `config.admin.permissions`. **[Справочник по схемам](blueprint-reference/index.md)** подробно объясняет, как его написать.

## Две классические ловушки

Две ошибки ловят почти каждого, кто пишет первую схему Flex. Обе происходят из отношения к схеме Flex как к обычной форме Grav.

**Не используйте простой формат списка полей.** Формы Grav позволяют описывать поля обычным списком (формат, показанный в **[Создании простой одиночной формы](../../../forms/forms/index.md)**). Flex не поддерживает такое сокращение. Всегда пишите `form.fields` как карту ключей, где ключ поля — его имя, а значение — конфигурация поля, точно как в примерах выше.

**Не включайте в форму раздел `process`.** Обычная форма Grav использует блок `process`, чтобы определить, что происходит при отправке (отправить письмо, сохранить в файл и т. д.). Flex полностью игнорирует этот раздел, потому что сохранением занимается слой хранения. Добавление его ничего не делает и только вызывает путаницу, поэтому не включайте его.

> [!WARNING] Предупреждение
> Будьте осторожны, меняя схему типа, у которого уже есть сохранённые записи. Убедитесь, что существующие объекты по-прежнему чисто загружаются и сохраняются по новой схеме. Переименование или удаление поля может оставить старые записи неотображаемыми.
