# Flex-объекты

**Flex** — это фреймворк Grav для пользовательских структурированных данных. Он даёт единообразный способ хранить, запрашивать, редактировать и отображать коллекции записей (товары, события, участники команды, адресную книгу, заявки в поддержку — что угодно), которые плохо вписываются в дерево страниц или файл конфигурации.

У Flex две половины, работающие вместе:

* Основной **фреймворк Flex** (`Grav\Framework\Flex`), который поставляется вместе с самим Grav. Он определяет объекты, коллекции, индексы и слои хранения, на которых построено всё остальное.
* Плагин **Flex Objects**, который превращает этот фреймворк в продукт, пригодный к использованию без написания PHP. Плагин даёт регистрацию пользовательских директорий, интерфейс **Admin Next** для управления по CRUD, REST API, шорткод `[flex-objects]`, а также маршрутизацию страниц фронтенда и шаблоны.

> [!NOTE] Примечание
> **Директории Flex** в этой документации не имеют отношения к старому плагину **Flex Directories**. Тот плагин был заменён фреймворком Flex вместе с плагином Flex Objects.

## Какую задачу решает Flex?

Рано или поздно любому сайту Grav нужны данные, которые не являются ни страницей, ни настройкой. Страница отлично подходит для редакционного контента с URL, текстом и медиафайлами. Файл конфигурации хорош для нескольких параметров, которые редко меняются. Но список из пятисот товаров, система бронирования или справочник участников — ни то, ни другое. Моделировать такие данные страницами быстро становится неудобно (одна папка на запись, никаких настоящих запросов, никаких структурированных полей), а файлы конфигурации никогда не предназначались для хранения записей.

Flex закрывает эту брешь. Вы один раз описываете данные в **схеме** (её поля, форму, хранилище, права доступа), а Flex даёт остальное: редактируемый раздел админки, коллекционный API с запросами в PHP и Twig, REST API и рендеринг на фронтенде. Одно и то же определение объекта питает каждую точку доступа, поэтому форма в админке, данные в API и шаблон Twig одинаково представляют, как выглядит запись.

## Когда использовать Flex

Flex — один из нескольких способов хранить данные в Grav. Выбирайте инструмент под задачу.

| Используйте         | Когда                                                                                                                        |
| :---------------- | :-------------------------------------------------------------------------------------------------------------------------- |
| **Страницы**         | Запись — это редакционный контент, которому нужны собственный URL, текст и медиафайлы (запись блога, лендинг, статья документации). |
| **Конфигурация / YAML** | У вас небольшой, в основном статичный набор параметров, которые изредка правит человек, собирающий сайт (название сайта, ключи API, фича-флаги). |
| **Учётные записи**      | Вы храните пользователей для входа. Система учётных записей сама по себе — встроенный тип Flex, поэтому записи пользователей вы получаете бесплатно, ничего не определяя. |
| **Flex**          | У вас много структурированных записей одного вида, которым нужны запросы, интерфейс редактирования, API или всё сразу, и это не контент, адресуемый в первую очередь по URL. |

Полезное правило: если на другой платформе вы бы взяли таблицу базы данных, здесь, скорее всего, нужен тип Flex.

## Встроенные типы

Вы уже используете Flex, даже если никогда не определяли тип. Под капотом несколько основных систем — это директории Flex:

* **Страницы** опираются на тип Flex, и именно это позволяет Admin Next единообразно выводить их списком, искать и редактировать.
* **Учётные записи пользователей** — это тип Flex. Каждая учётная запись, которой вы управляете в админке, — Flex-объект.
* **Группы пользователей** тоже тип Flex.

Поскольку это настоящие директории Flex, их можно запрашивать из Twig и PHP тем же коллекционным API, который вы используете для своих типов. Чтобы читать встроенные версии Flex для учётных записей или страниц, ничего специально включать не нужно.

## Словарь понятий

Flex вводит несколько терминов. Они чётко соотносятся друг с другом, поэтому стоит прочитать их один раз перед началом работы.

#### Flex

**Flex** — контейнер для всех ваших **директорий Flex**. Это единая точка доступа ко всем зарегистрированным директориям сайта, что делает все эти данные доступными с любой страницы, из плагина или шаблона.

#### Тип Flex

**Тип Flex** — схема для директории. Он определяет всё необходимое для хранения, отображения и изменения данных: структуру данных, поля формы, права доступа, файлы шаблонов и слой хранения. Тип описывается в YAML-файле схемы (см. [Создание своего типа](custom-types/index.md)).

#### Директория Flex

**Директория Flex** содержит коллекцию **Flex-объектов**, у которых общий **тип Flex**. Каждая директория управляет **коллекцией** **объектов** и, необязательно, **индексом**, ускоряющим запросы к её **хранилищу**.

#### Коллекция Flex

**Коллекция Flex** — структура, содержащая **Flex-объекты**. На практике коллекция обычно содержит только объекты, нужные для текущей страницы или действия. Она даёт инструменты для фильтрации и работы с данными, а также методы для рендеринга всего набора сразу.

#### Flex-объект

**Flex-объект** — отдельный экземпляр **типа Flex**, представляющий одну запись. Объект даёт доступ к своим свойствам, включая связанные данные, например [медиафайлы](../../content/media/index.md). Он также знает, как отрендерить себя и какую форму использовать для редактирования. Создание, обновление и удаление обрабатывает сам объект.

#### Индекс Flex

**Индекс Flex** делает запросы к директории быстрыми. Он хранит облегчённые метаданные об объектах (достаточные для сортировки, фильтрации и постраничного вывода), не загружая полные объекты в память.

#### Хранилище Flex

**Хранилище Flex** — слой, который сохраняет объекты. Это может быть один общий файл, один файл на объект в папке или одна папка на объект. Flex также поддерживает пользовательские бэкенды хранения, например базу данных. Выбранная стратегия влияет на то, может ли тип иметь медиафайлы для отдельных объектов (см. [Как работает Flex](concepts/index.md)).

#### Форма Flex

**Форма Flex** интегрируется с плагином Form, чтобы можно было создавать или редактировать Flex-объект. Flex поддерживает несколько представлений, позволяя разным частям объекта редактироваться разными формами.

#### Администрирование Flex

**Администрирование Flex** обеспечивает плагин Flex Objects. Он добавляет раздел в **Admin Next**, где администраторы сайта управляют Flex-объектами. Каждая директория поставляется с разрешениями в стиле CRUD, поэтому можно ограничить вывод списка, чтение, создание, обновление и удаление для конкретных пользователей. См. [Управление Flex в Admin Next](administration/index.md).

## Текущие ограничения

Flex мощен, но подходит не для любой задачи. Учитывайте эти ограничения при планировании типа:

* Flex **основан на индексе**, поэтому он не идеален для наборов данных с очень высокой частотой записи, которые постоянно обновляются. Для записи, меняющейся много раз в секунду, лучше подойдёт специализированная база данных.
* Настройка поведения **за пределами того, что может выразить схема** (пользовательские запросы, вычисляемые свойства, собственное хранилище, нетривиальная валидация), требует написания PHP-классов. См. [Расширение Flex на PHP](php-and-events/index.md).
* Поддержка **мультиязычности** сильнее всего для **страниц**. Пользовательские типы могут хранить переводимые поля, но полного паритета с обработкой мультиязычности страниц в Grav пока нет.

Ничто из этого не должно мешать создавать с помощью Flex большинство фич на основе данных. Это просто границы, о которых стоит знать до того, как вы зафиксируете проект.
