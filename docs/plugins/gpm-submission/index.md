# Публикация в GPM

Когда вы создали новый плагин и хотите добавить его в [репозиторий Grav](https://getgrav.org/downloads), чтобы его можно было установить через **GPM** и **админку**, нужно учесть несколько стандартных требований. Эта страница состоит из двух частей: сначала **публикация плагина** в GPM, затем **его сопровождение** после добавления в список — выпуск обновлений и протокол принятия заброшенных плагинов. Если вы публикуете тему, см. [версию этой страницы для тем](../../themes/gpm-submission/index.md), где также описана упаковка полного демонстрационного сайта в виде скелета.

## Часть 1: Публикация плагина

### Требования к плагину

Правильный плагин Grav требует определённых файлов, чтобы работать должным образом, быть указанным в репозитории Grav и отображаться в админке Grav. Убедитесь, что ваш плагин содержит все эти файлы:

* **yourplugin.php** — PHP-файл плагина, имя которого должно совпадать с именем папки
* **yourplugin.yaml** — файл конфигурации плагина, содержащий параметры и информацию о наследовании потоков
* **blueprints.yaml** — файл определения плагина и файл определения формы
* **CHANGELOG.md** — файл изменений в правильном формате Grav для единообразного отображения
* **README.md** — обязательный файл для описания и предварительного просмотра плагина
* **LICENSE** — файл лицензии, вероятно MIT, если совместим с ядром Grav
* **languages.yaml** (необязательно) — файл определения языка

В отличие от тем, плагинам **не** нужны изображения `screenshot.jpg` или `thumbnail.jpg` — плагин визуально представлен иконкой Font Awesome `icon:`, объявленной в его `blueprints.yaml`, как на getgrav.org, так и в списке плагинов админки.

### Файл blueprints.yaml {: #the-blueprints-yaml-file }

Файл `blueprints.yaml` в корне плагина — то, что читают GPM и админка, чтобы представить ваш плагин. Реальный пример из плагина **Breadcrumbs**:

```yaml
name: Breadcrumbs
type: plugin
slug: breadcrumbs
version: 1.6.3
description: The **Breadcrumbs** plugin provides a simple method to display the depth of your content/navigation structure.
icon: caret-square-o-right
author:
  name: Team Grav
  email: devs@getgrav.org
  url: https://getgrav.org
homepage: https://github.com/getgrav/grav-plugin-breadcrumbs
demo: https://demo.getgrav.org/blog-skeleton
keywords: breadcrumbs, plugin, navigation, depth
bugs: https://github.com/getgrav/grav-plugin-breadcrumbs/issues
license: MIT
compatibility:
  grav: ['1.7', '2.0']

dependencies:
  - { name: grav, version: '>=1.7.0' }
```

Поля `name`, `slug`, `type`, `version`, `description`, `author` и `license` обязательны для листинга в GPM. Полный справочник полей, включая раздел `form:`, определяющий параметры конфигурации плагина в админке, см. в [схемах](../../forms/blueprints/index.md).

> [!NOTE] Примечание
> Плагины для Grav 2.0 должны объявлять раздел `compatibility:`, чтобы GPM и мастер миграции знали, какие мажорные версии Grav поддерживает плагин. Подробности см. в разделе [Совместимость плагинов](../plugin-compatibility/index.md).

### Процесс выпуска

Когда плагин готов к добавлению в репозиторий, пройдите этот контрольный список:

1. Открытый исходный код с файлом `LICENSE`, предоставляющим лицензию, совместимую с [MIT](http://en.wikipedia.org/wiki/MIT_License). [Пример здесь](https://github.com/getgrav/grav-plugin-breadcrumbs/blob/develop/LICENSE)
2. Содержит файл `README.md` с описанием функциональности и инструкциями по установке и настройке. [Пример здесь](https://github.com/getgrav/grav-plugin-breadcrumbs/blob/develop/README.md)
3. Содержит файл `blueprints.yaml` со [всеми обязательными полями](../../forms/blueprints/index.md). [Пример здесь](https://github.com/getgrav/grav-plugin-breadcrumbs/blob/develop/blueprints.yaml)
4. Предоставляет `CHANGELOG.md` в [правильном формате](#changelog-format). [Пример здесь](https://github.com/getgrav/grav-plugin-breadcrumbs/blob/develop/CHANGELOG.md)
5. Указывает соответствующую атрибуцию, если вы используете другие библиотеки, скрипты или код.
6. [Создайте релиз](https://docs.github.com/en/repositories/releasing-projects-on-github) готового плагина. Система репозитория Grav требует релиз и не найдёт ваш плагин, если нет релиза, содержащего всё перечисленное.
7. [Добавьте issue в трекер Grav](https://github.com/getgrav/grav/issues/new?title=[add-resource]%20New%20Plugin/Theme&body=I%20would%20like%20to%20add%20my%20new%20plugin/theme%20to%20the%20Grav%20Repository.%0AHere%20are%20the%20project%20details:%20**user/repository**) с подробностями о плагине, и мы быстро проверим его работоспособность, после чего добавим.

### Формат списка изменений {: #changelog-format }

Сайт GetGrav.org использует собственный формат ChangeLog, написанный в стандартном Markdown, но который можно обработать простым CSS и [отобразить в привлекательном виде](https://getgrav.org/downloads#changelog). Чтобы ваши ChangeLog корректно разбирались и форматировались, используйте этот синтаксис:

```markdown linenums="1"
# X.Y.Z
## 2015-01-01

1. [](#new)
    * New features added
    * Another new feature
2. [](#improved)
    * Improvement made
    * Another improvement
3. [](#bugfix)
     * Bugfix implemented
     * Another bugfix

...repeat...
```

Каждый раздел `#new, #improved, #bugfix` необязателен; включайте только нужные разделы.

> [!TIP] Совет
> Версии могут быть `vX.Y.Z` или `X.Y.Z`, главное — согласованность между релизами. Убедитесь, что версия идёт с `#`, а дата с `##`, каждая на своей строке, и между этими заголовками и списками ниже есть пустая строка. Также убедитесь, что элементы списка имеют одинаковый отступ.

> [!NOTE] Примечание
> **Используйте формат даты ISO `YYYY-MM-DD`.** Это единственный формат, который нельзя прочитать неправильно. **Американский** `MM/DD/YYYY` и **европейский** `DD-MM-YYYY` форматы также принимаются, и большинство существующих списков изменений используют их, но помните, что **только разделитель** определяет, как читается дата, независимо от задуманного порядка: слэш (`/`) означает американский порядок «месяц первым», а дефис (`-`) или точка (`.`) означают европейский порядок «день первым». То же правило для заголовков страниц см. в разделе [форматы дат](../../content/headers/index.md#date).

> [!WARNING] Предупреждение
> Поскольку всё решает разделитель, дата в формате «день первым», записанная со слэшами, читается как «месяц первым». Обычно это замечают, так как значение больше 12 не может быть месяцем, поэтому `13/08/2026` всё равно понимается как 13 августа. Но когда оба числа не больше 12, ничего не выглядит неправильным: `11/08/2026` читается как 8 ноября, а не 11 августа, и предупреждение не появляется. Запись дат в формате `YYYY-MM-DD` избегает всей этой проблемы.

### Демонстрационный контент

Вы можете предоставить демонстрационный контент как часть пакета плагина. Это значит, что всё, что находится в папке `_demo/`, будет скопировано в папку `user/` в процессе установки. Так можно предоставить **страницы**, **конфигурацию** или что угодно ещё, что находится в папке `user/`. Пользователю будет предложено сделать это, и это совершенно необязательно.

_Обратите внимание: демонстрационный контент не копируется при установке плагина через **админку**._

## Часть 2: Обновления и сопровождение

### Выпуск обновлений

После того как плагин добавлен в репозиторий, **не** нужно открывать issue для новых версий. Измените `version:` в `blueprints.yaml`, добавьте соответствующую запись в `CHANGELOG.md` и опубликуйте новый релиз GitHub — GPM подхватит его автоматически, а пользователи увидят обновление в админке и через `bin/gpm update`.

> [!WARNING] Предупреждение
> Убедитесь, что **именование каждого тега согласовано**. GPM использует эту информацию, чтобы определить, новее ли ваш плагин предыдущего. Рекомендуем использовать [семантические номера версий](http://semver.org/) для тегов. Например, `1.2.4`. Согласованность всех тегов критически важна — смешивание стилей `v1.2.4` и `1.2.5` сломает обнаружение обновлений!

### Протокол заброшенных ресурсов

Люди идут дальше, и созданный пользователями контент, например плагины, может остаться без поддержки. Если вы хотите взять на себя поддержку существующего плагина, необходимо следовать этому протоколу:

1. Отправьте хорошо оформленный и протестированный pull request в исходный репозиторий.

2. Если сопровождающий *вообще* не отвечает в течение 30 дней или заявляет, что забрасывает ресурс и не готов предоставить кому-то другому доступ на запись, переходите к следующему шагу.

3. [Отправьте новый issue в репозиторий Grav на GitHub](https://github.com/getgrav/grav/issues/new?title=%5Bchange-resource%5D%20Take%20over%20Plugin%2FTheme&body=I%20would%20like%20to%20take%20over%20an%20existing%20plugin%2Ftheme.%0AHere%20are%20the%20project%20details%3A%20%2A%2Auser%2Frepository%2A%2A) со следующими сведениями:

  * Заголовок: `[change-resource] Take over plugin/theme`

  * Укажите название плагина и ссылку на исходный репозиторий.

  * Дайте ссылку на ваш pull request, оставшийся без ответа, или на обсуждение, в котором сопровождающий отказался от ресурса.

4. Сопровождающие Grav рассмотрят случай и сообщат, одобрено ли принятие. Если одобрено, переходите к следующему шагу.

5. Подготовьте форк репозитория с новым релизом.

6. Добавьте в README примечание, что этот репозиторий теперь основной, и ссылку на старый репозиторий.

7. Ответьте в issue, сообщив сопровождающим новый URL плагина.

8. Сопровождающие обновят GPM, и новые и обновлённые установки будут происходить из вашего форка.
